# 周报逐人提炼契约加固设计

## 背景

任务 `4c6b3d9a-0fb5-4179-97de-19a3f31bd4ef` 在 `extract_person:P01` 失败。模型服务两次均返回 HTTP 200，但首次响应使用 `tasks_completed`，缺少约定的 `facts`；自动修复后的响应虽然通过 JSON Schema 校验，却把身份从 `P01 / 周五` 改成 `P02 / 周六`。应用层身份校验拒绝入库，并把无专用错误码的异常统一记录为 `PERSON_EXTRACTION_FAILED`。

当前问题不是连接稳定性问题，而是系统把人员身份、事实 ID 等确定性数据交给了概率模型生成，同时修复请求只携带错误响应和 Schema，没有携带原人员身份及带行号原文。

## 目标

1. 人员编号、姓名、事实 ID 和事实来源人员编号由服务端确定，不接受模型改写。
2. 首次响应结构错误时，修复请求仍携带当前人员身份和带行号原文。
3. 修复后的事实必须重新经过结构校验和服务端绑定，不能跨人员污染。
4. 结构化响应最终仍无效时，步骤保存可定位的错误码，日志记录阶段和人员编号，但不记录周报正文、模型原文或人员姓名。
5. 保持现有 OpenAI 兼容接口、一次自动修复和断点重试流程不变。

## 非目标

- 不增加新的模型供应商或模型参数。
- 不增加额外的模型重试次数。
- 不修改人员识别、跨人员聚合、模板成稿或 Word 导出逻辑。
- 不在数据库或日志中保存模型原始响应。
- 不自动重试或改写当前失败任务；代码部署后仍由现有重试入口恢复。

## 方案比较

### 方案 A：仅加强提示词

在提示词中重复强调字段和身份。改动最小，但本地模型仍可能忽略 Schema 或在修复时改写身份，无法建立确定性保证。

### 方案 B：仅覆盖人员身份

解析完成后把 `person_id` 和 `person_name` 改回请求值。可以绕过本次身份漂移，但模型仍可能为不同人员重复生成 `F1` 等事实 ID，修复请求也可能生成缺少原文依据的引用。

### 方案 C：服务端绑定确定性字段并补全修复上下文

模型只生成事实语义，服务端统一绑定身份、来源人员编号和事实 ID；修复请求重新提供人员身份与带行号原文；最终结构失败使用专用错误码。该方案同时消除身份漂移、事实 ID 冲突和修复失去原文上下文的问题，因此采用此方案。

## 数据流

1. `OpenAICompatibleClient.extract_person` 使用现有逐人提示词请求模型。
2. 响应通过 `PersonExtraction` Schema 校验后返回。
3. 若首次校验失败，客户端调用新的人员感知修复提示：
   - 明确期望的 `person_id` 和 `person_name`；
   - 重新提供与首次请求一致的带行号原文；
   - 提供 Schema 和待修复响应；
   - 要求不得添加原文中不存在的事实。
4. 修复结果再次通过 `PersonExtraction` Schema 校验。
5. `AnalysisService` 在持久化前执行服务端绑定：
   - `person_id` 固定为当前人员 ID；
   - `person_name` 固定为当前人员姓名；
   - 每个事实 ID 按输出顺序固定为 `<person_id>-F01`、`<person_id>-F02`；
   - 每个来源的 `person_id` 固定为当前人员 ID；
   - 模型生成的事实类型、主题、正文、指标、行号、引用和置信度保持不变。
6. 绑定后的结果执行现有防御性身份校验并写入数据库。

服务端覆盖的字段都是请求上下文中已有的确定性元数据，不改变模型提炼出的业务事实。为不同人员生成带人员前缀的事实 ID，可避免 `(task_id, fact_id)` 主键冲突。

## 错误处理与可观测性

`InvalidStructuredResponse` 增加稳定错误码 `MODEL_SCHEMA_INVALID`。首次解析失败但自动修复成功时不标记步骤失败；自动修复后仍无法通过 Schema 时，步骤记录 `MODEL_SCHEMA_INVALID`。

分析服务捕获失败时增加一条脱敏结构化日志，只包含：

- `stage=person_extraction`
- `entity_id=Pxx`
- `error_code`

日志白名单新增 `entity_id`，不新增错误正文、人员姓名、周报内容或模型响应。

模型连接、认证、超时、模型不存在等现有专用错误码保持不变。无法识别的应用异常仍回退为 `PERSON_EXTRACTION_FAILED`。

## 兼容性

- `PersonExtraction` 对外结构不变。
- LLM 协议和数据库结构不变，不需要迁移。
- 事实 ID 仍是字符串，只是由后端统一为既有测试中已使用的 `P01-F01` 格式。
- 已成功的人员步骤继续由断点逻辑跳过；失败步骤可以通过现有“重试当前步骤”重新执行。
- Windows 和 Linux 部署产物无需新增依赖或配置项。

## 测试与验收

1. 单元测试复现修复结果把 `P01 / 张三` 改成其他身份，验证最终结果仍绑定为 `P01 / 张三`。
2. 单元测试验证来源中的错误人员编号被绑定为当前人员。
3. 单元测试验证事实 ID 被稳定重写为 `P01-F01`、`P01-F02`，不同人员不会产生同一事实 ID。
4. 提示词测试验证修复请求包含期望身份、带行号原文、Schema 和待修复响应。
5. 单元测试验证两次结构校验都失败时抛出 `MODEL_SCHEMA_INVALID`。
6. 应用测试验证专用错误码写入 `job_steps`，脱敏日志不包含姓名、正文和模型原始响应。
7. 运行完整后端测试、静态检查和前端测试，确认无回归。
8. 使用当前 P01、当前本地模型执行只读提炼，验证结果身份和事实 ID 正确。
9. 部署并重启服务后，由现有重试入口恢复当前任务，确认 P01 成功并继续处理后续人员。
